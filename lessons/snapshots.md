# Snapshots

- 17 Nov 2026: snapper's NUMBER_LIMIT was CachyOS's 50, for root and home. The rules hook takes a pre and post pair for every change it cannot prove read-only, and snapper's cleanup counts every pre and post before it removes empty pairs (order: number, timeline, empty-pre-post; hourly timer). So 50 kept only the last ~25 commands, and real changes (snap-pac pairs for package installs) were gone within an hour or two. Now NUMBER_LIMIT="50-500" for both: keeps up to 500, and FREE_LIMIT=0.2 (live only when the limit is a range) falls back towards 50 below 20% free. Set with `snapper -c root set-config`; repo copies in config/snapper/, installed by sidekick/install.sh. Quotas are off, so SPACE_LIMIT is inert. Reviewer: CONCERNS, answered.
- Boot menu (limine-snapper-sync 1.32.1): `MAX_SNAPSHOT_ENTRIES` counts snapshots, prunes oldest first, never re-adds a dropped entry, and never deletes snapper snapshots. `restore` (limine-snapper-restore) only finds snapshots in its menu manifest. Added to /etc/limine-snapper-sync.conf: `EXCLUDE_SNAPSHOT_TYPES="post"` and `MAX_SNAPSHOT_ENTRIES=30`, so the menu holds the state before each of the last changes. Check with `sudo limine-snapper-info`. Backup of the file before: ~/.cache/kiln-limine-backup/limine-snapper-sync.conf.2026-11-17.
- Older states than the menu holds: use `snapper` by hand (the snapshots are kept up to 500).
- Known fault, not yet fixed (reviewer, 17 Nov): `undo` looks up the newest logged change; if its pair was already removed as empty, `snapper status` fails and undo stops instead of trying the change before. Better root fix, for a reviewed change to kiln_rules.py (owner installs): the hook deletes its own pair at once when it is empty, so empty pairs never fill the counts.
- Home snapshots pin deleted data (e.g. the 27 GB kernel build trees in ~/.cache/kiln-kernel) until the pair ages out. A separate subvolume for ~/.cache would keep build trees out of snapshots; not done.
